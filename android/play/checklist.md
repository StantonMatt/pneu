# First Google Play closed test

Owner checklist for version 2.2.0 (7), application ID `io.github.stantonmatt.pneu`. Policy references checked 2026-10-25. No Console account or release has been created by this task.

1. **Register a personal developer account.** Use your chosen Google account, accept the agreement and pay the one-time US$25 fee. Complete identity/contact verification and any Android-device verification in the Play Console mobile app. These owner sign-in/physical-device actions must be done by the owner. Choose public developer details deliberately. [Account setup](https://support.google.com/googleplay/android-developer/answer/6112435).
2. **Resolve the pre-submission privacy gap.** Publish [PRIVACY.md](../../PRIVACY.md) so https://github.com/StantonMatt/pneu/blob/main/PRIVACY.md loads publicly without sign-in. Add an accessible privacy-policy link inside the app, then build and verify that change before uploading. This task's permitted UI edits cover only battery setup, so the current APK does not add that link. Also verify that setup clearly explains automatic background media sending before permissions; add a specific disclosure/consent step if the existing setup does not meet the policy. [User Data requirements](https://support.google.com/googleplay/android-developer/answer/10144311).
3. **Back up the upload key privately.** Files are outside Git in `~/.local/share/android-release-keys/pneu/`: `upload.jks`, `keystore.properties`, `upload-certificate.pem`. Keep an encrypted independent backup of the keystore and credentials. Never upload the private key or properties to GitHub, Play listing text or a support issue. The public PEM certificate is safe to register with Play. Keep the private directory at mode 700 and files at 600.
4. **Create the app in Console.** Name Pneu, default language English (United States), App, Free, and accept the policy/export declarations after reading them. Keep the existing package ID. The store category suggestion is Tools. Once published as free, an app cannot simply be changed to paid.
5. **Complete the store listing.** Paste [listing.md](listing.md); supply the owner's monitored public support email (still needed). Upload `graphics/icon-512.png`, `graphics/feature-graphic.png` and the seven phone screenshots in `screenshots/`, in file-name order. They are 1080×1920, which meets [Play's asset requirements](https://support.google.com/googleplay/android-developer/answer/9866151). Confirm the website/download links work and accurately list desktop platforms.
6. **Complete App content.** Enter the privacy-policy URL, Data safety answers from [data-safety.md](data-safety.md), ads No, age target 18+, IARC questionnaire, reviewer access instructions and the permission/FGS declarations in [declarations.md](declarations.md). Upload the foreground-service demo video (kept outside the repo; ask for `pneu-fgs-demo.mp4`) to YouTube as unlisted and paste its link into the declaration. Select **No** for collection/sharing: Pneu collects and shares no data. Its transfers stay between the user’s paired devices, encrypted in transit. Complete any other Console prompts applicable to your account (government, news, health and financial features: none).
7. **Build the reviewed candidate.** From `android/`, run `/home/mjstanton/.local/bin/heavy ./gradlew bundleRelease assembleRelease lintRelease`. Debug/unit/lint/instrumentation-APK gate: `/home/mjstanton/.local/bin/heavy ./gradlew assembleDebug testDebugUnitTest lintDebug assembleDebugAndroidTest`. Use a fresh versionCode for each different upload; this candidate uses 7 and versionName 2.2.0. After the required privacy UI follow-up, rerun affected checks, release smoke and the implementing agent's required review before committing/pushing. This implementation worker has not run a review loop.
8. **Enroll in Play App Signing on the first release.** In the closed-test release flow, let Google generate and securely hold the **app signing key**. Upload `app/build/outputs/bundle/release/app-release.aab`, signed locally by the separate **upload key**. Register/confirm the upload certificate if prompted using `upload-certificate.pem` or its SHA-256. Do not choose a flow that uploads the upload private key as your permanent app-signing key by mistake. Compare the upload certificate shown under App integrity with the local certificate. [Play App Signing](https://support.google.com/googleplay/android-developer/answer/9842756).
9. **Check signing consequences.** Play-delivered APKs are signed by Google's app signing key, so they will not update an existing debug, sideloaded or locally upload-key-signed APK with a different certificate. Testers may need to uninstall their existing install first, which removes private app data and pairings; they must pair again. Save received files independently. Do not distribute the local release APK as a substitute for joining the Play closed test.
10. **Create the closed track and testers.** Choose the test countries/regions and create a tester email list (Google-account addresses) or a Google Group you control. For a Group, testers must first join with the same Google account they use in Play. Recruit more than 12 eligible adult testers with Android 14+ and access to a Linux or macOS computer. Set a private feedback channel and keep the release on the closed track. [Test-track setup](https://support.google.com/googleplay/android-developer/answer/9845334).
11. **Submit and start the test.** Add the AAB and en-US release notes; inspect Console errors, native-library/page-size checks, permission reviews and the pre-launch report. Submit for review and roll out to the closed track when approved. Copy the track's opt-in link after it is available. Send testers that link and desktop setup instructions. They must open it with their allowed Google account, explicitly opt in, then install from Google Play. Being on the email list or Group alone does not opt them in. Internal testing does not satisfy the production-access requirement.
12. **Run at least 14 consecutive days with at least 12 opted-in testers.** For a newly created personal account, at least 12 testers must remain opted in continuously for the preceding 14 days when you apply. Track the Console eligibility indicator and maintain a buffer against opt-outs. Ask testers to exercise pairing, manual clipboard, background screenshot/photo/recording sending, received files, notifications, battery settings and LAN/Tailscale transitions. Collect real feedback and record fixes and retests; an install count alone is insufficient evidence of engagement. [Personal-account production access](https://support.google.com/googleplay/android-developer/answer/14151465).
13. **Apply for production access.** Once Console confirms eligibility, use Dashboard → Apply for production. Answer using actual tester recruitment/engagement, collected feedback, changes made, intended audience, app value and readiness evidence. Do not paste invented feedback or claim that 14 days guarantees approval. Google may request more testing. After access is granted, create a production release and follow its separate review/rollout steps; closed testing does not automatically publish to production.

## Technical acceptance to retain

- Minimum SDK stays 34. Target SDK 37 exceeds the currently documented new-app minimum of API 36 from August 31, 2026. [Target API requirement](https://support.google.com/googleplay/android-developer/answer/11926878).
- Keep R8/minification off for this candidate. Validate reflection keep rules before enabling it later.
- Verify both APK ZIP alignment (`zipalign -c -P 16 -v 4`) and native ELF LOAD-segment alignment. ZXing core is pure Java and adds no native libraries. The documented Play requirement applies to 64-bit devices. Play must also validate the uploaded AAB's generated splits. [16 KB guidance](https://developer.android.com/guide/practices/page-sizes).
- Keep the signed artifact, certificate fingerprint, build/lint results and smoke evidence together. Do not confuse static 16 KB alignment checks or a 4 KB emulator smoke with execution on a 16 KB device.
